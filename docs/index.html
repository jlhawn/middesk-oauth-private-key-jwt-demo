Middesk API · OAuth 2.0

Private key JWT clients that rotate their own keys

A Node.js client authenticates to the Middesk API with RSA keys instead of a shared secret, holds 10-minute access tokens, and swaps in a new key without anyone touching an API key.

client_credentials private_key_jwt · RFC 7523 RS256 Node.js + jose

The goal

What the demo shows

1Asymmetric client auth

The OAuth client proves who it is with a JWT signed by its private RSA key. Middesk stores only the public key, so there's no secret to leak from either side.

2Short-lived tokens

The client's access_token_ttl is set to 600 seconds, so every access token expires after 10 minutes instead of the default hour.

3Self-service key rotation

The client registers a new key and retires the old one by signing the request with a key it already holds. No API key or access token is involved.

4Real API calls and an audit trail

The access token creates a business, and the security event logs API shows each rotation with the key IDs before and after.

Architecture

Three credentials, three jobs

Step 1 · bootstrap

Register the client with an API key, once

const k1 = await generateSigningKey('k1');

const client = await middesk.createOAuthClient(apiKey, {
  name: 'Key rotation demo',
  redirect_uri: 'https://example.com/oauth/unused',
  allowed_grant_types: ['client_credentials'],
  token_endpoint_auth_method: 'private_key_jwt',
  access_token_ttl: 600,
  jwks: { keys: [k1.publicJwk] },
});
  • generateSigningKey makes a 2048-bit RSA key pair with jose and exports the public half as a JWK with a kid.
  • private_key_jwt means the client can only authenticate with signed assertions. Middesk withholds its secret, so the response has secret: null.
  • access_token_ttl: 600 sets every token's lifetime to 10 minutes. The maximum is 24 hours.
  • This is the only call that needs the API key. The demo also uses it at the end to delete the client.

Step 2 · client assertion

A short-lived JWT, signed with the private key

const assertion = await new SignJWT({})
  .setProtectedHeader({ alg: 'RS256', kid: key.kid })
  .setIssuer(clientId)
  .setSubject(clientId)
  .setAudience(audience)
  .setIssuedAt()
  .setExpirationTime('2m')
  .setJti(randomUUID())
  .sign(key.privateKey);
ClaimRule
iss, subThe client_id
audThe endpoint it's presented to, such as https://api.middesk.com/oauth/token
jtiUnique. Middesk accepts each one once.
exp − iatAt most 10 minutes
kid headerPicks which registered public key verifies the signature

Trade the assertion for a 10-minute access token

// response
{
  "access_token": "…",
  "token_type": "Bearer",

  "scope": "read_write",
  "account_id": "…"
}

The token belongs to the client itself, with no user behind it. Sending the same assertion twice gets invalid_client, because its jti has already been used.

Step 4 · resource calls

Use the token like any bearer credential

await middesk.createBusiness(token.access_token, {
  name: 'Middesk Inc',
  addresses: [{
    address_line1: '85 Second Street',
    address_line2: 'Suite 710',
    city: 'San Francisco',
    state: 'CA',
    postal_code: '94105',
  }],
  orders: [{ package: 'identity' }],
});
await middesk.listSecurityEventLogs(token.access_token, {
  action: 'change_settings',
  include_payload: 'true',
});

// Authorization: Bearer <access_token>

Work done with the token is attributed to the client's account, the same as with an API key. API keys, user management and OAuth client management stay closed to OAuth tokens.

Step 5 · rotation

Rotate with an overlap: add, switch, retire

Deploy k2 to every instance between the two calls. Tokens already issued keep working until they expire.

Step 5 · rotation request

The client signs its own key change

async replaceJwks({ clientId, key, jwks }) {
  const path = `/oauth/clients/${clientId}/jwks`;
  const assertion = await clientAssertion({
    clientId,
    key,
    audience: `${this.issuer}${path}`,
  });

  return this.#form(path, {
    jwks: JSON.stringify(jwks),
    ...assertion,
  }, 'PUT');
}
# request
PUT /oauth/clients/<client_id>/jwks
Content-Type: application/x-www-form-urlencoded

client_assertion_type=urn:ietf:...:jwt-bearer
&client_assertion=<JWT signed with k1>
&jwks={"keys":[{"kid":"k1",...},{"kid":"k2",...}]}

# response 200
{ "client_id": "…", "jwks": { "keys": [ … ] } }

Rules the endpoint enforces

Guard rails on key changes

Its own audience

Assertions must name …/oauth/clients/<id>/jwks. The token endpoint won't accept them, and this endpoint won't accept token assertions.

Single use

Every jti is recorded, and lifetimes over 10 minutes are refused, so a captured assertion can't be replayed.

Keep the signing key

The new set must still contain the key that signed the request, with the same material. A client can't upload a key set it holds no key for.

Only jwks

The redirect URI, grant types, token lifetime and auth method still need the account's API key or the dashboard.

private_key_jwt only

Secret-based clients are refused. Keys they stored would become trusted the moment an admin switched them to private_key_jwt, outliving the secret.

Audited

Every change writes a change_settings security event with the client ID and the key IDs before and after.

Design choice

Why rotation doesn't accept a bearer token

Rotating with an access token

A leaked 10-minute token could add an attacker's key, turning a short-lived credential into a permanent one.

Rotating with a signed assertion

Each change proves possession of a registered private key, in a single-use JWT addressed to this endpoint only.

Client credentials authenticate only on the /oauth endpoints that manage credentials (token, revoke and jwks). Everything under /v1 uses tokens.

Step 6 · audit

Both rotations show up in the security event logs

GET /v1/security_event_logs?action=change_settings&include_payload=true
Authorization: Bearer <token signed by k2>

{
  "action": "change_settings",
  "payload": {
    "scope": "oauth_client",
    "oauth_client_id": "…",
    "old_settings": { "jwks_kids": ["k1"] },
    "new_settings": { "jwks_kids": ["k1", "k2"] }
  }
}

Events are written by a background job, so the demo polls for a few seconds until both appear.

The whole flow, end to end

   token_endpoint_auth_method: private_key_jwt · access_token_ttl: 600s · secret: null
2. Token from an assertion signed by k1        expires_in: 600s · scope: read_write
3. Business created with the access token      status: open
4. Rotate, part 1: register k2, signed with k1   registered kids: [k1, k2]
5. Token from an assertion signed by k2        expires_in: 600s
6. Guard rail: drop the signing key            400 invalid_client_metadata
7. Rotate, part 2: retire k1, signed with k2     registered kids: [k2]
8. Old key: token request signed by k1         401 invalid_client
9. Audit: change_settings  k1 → k1,k2

Run it yourself

Try it

npm install
cp .env.example .env
# set MIDDESK_API_URL and MIDDESK_API_KEY
npm run demo
  • Node.js 20 or later. The only dependency is jose.
  • The account needs fewer than five OAuth clients, and the package in MIDDESK_PACKAGE enabled (identity by default).
  • In live mode, step 3 creates a real, billed business. The demo deletes its OAuth client when it's done.
